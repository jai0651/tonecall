The problem

Two AI voice agents on the same call do this every turn: 

Agent A                       Agent B
   ↓ TTS         500 ms
   ↓ audio       300 ms (across PSTN)
                                ↓ STT         800 ms
                                ↓ LLM       1,500 ms
                                ↓ TTS         500 ms
   ↓ audio       300 ms (back)
   ↓ STT         800 ms

                  ≈ 4–5 seconds per turn

A 7-turn order takes 30–60 seconds. STT mis-hears "extra cheese" as "extra Swiss." Both sides pay TTS + STT + LLM + PSTN — every turn.

Beat: "This is the cost. Every turn round-trips through TTS, audio, STT, LLM. 4 to 5 seconds. Errors at every step. Both sides pay for every minute and every token."

If both sides are AI agents,

the audio channel is wasted bandwidth.

They could just exchange JSON.

They only need the audio channel for humans.

The insight slide. Pause for a beat. This is the wedge — phrase it confidently. "TTS and STT exist because phones carry audio. But when both ends are AI, audio is the lossy serialization layer. Just send JSON."

What Tonecall does

Two agents meet on a call · they detect each other · they switch to JSON. 

Without Tonecall                With Tonecall
─────────────────               ─────────────────
A ──voice── B   (45 s)          A ──voice intro── B    (8 s)
                                A ────JSON────── B    (0.5 s)
                                A ──voice goodbye── B (4 s)

slow + expensive                fast + cheap

The voice channel stays open — if a human walks in, the agents drop back to spoken English. The data flows over a WebSocket at internet speed.

Show the contrast. Emphasize: the voice channel stays available. The protocol degrades gracefully back to voice when needed. Worst case it behaves exactly like today's voice agents. Best case it closes the deal in a second.

How they recognize each other

The handshake (today's path): 

┌────────────┐                                ┌────────────┐
│  Agent A   │   ① both legs hit the broker   │  Agent B   │
│  Plivo DID │ ←──── shared coordination ────→│  Plivo DID │
└─────┬──────┘            key                 └─────┬──────┘
      │                                              │
      │     ② broker pairs them — same sessionId    │
      │                                              │
      │       ③ data WebSocket opens between        │
      │          the two agents over the broker     │
      │                                              │
      └────────────── JSON over WS ──────────────────┘

     Voice channel stays bridged via Plivo Conference (in case
     a human joins, or for the spoken intro/goodbye).

Cross-vendor variant: in-band DTMF preamble 9090<nonce># over real PSTN → ✓ verified, ships in v1.

The mechanism. Don't over-explain — judges respect concrete answers but not lectures. Three steps: both legs reach the broker with a shared key, broker pairs them, data WebSocket opens. The "verified" line is important. We probed it 2 hours ago — DTMF crosses a Dial bridge cleanly. That's the cross-vendor path; ships in v1 (post-hackathon). If anyone asks "what's the shared coordination key?" — say it's a deterministic name derived from the two DIDs today, and an in-band DTMF nonce in the cross-vendor version.

Why this is a protocol, not a product

AVIP-0 — Agent Voice Interop Protocol v0

Cross-vendor Any AI agent on any CPaaS (Plivo, Twilio, Telnyx…) can implement it.
Transport-agnostic PSTN today · direct WebSocket tomorrow · SIP-headers between.
Trust-extensible Per-domain /.well-known/avip + HMAC signing — DKIM-style.
Backwards-compatible Peer doesn't speak it? Falls back to voice automatically.

Plivo can own this the way Twilio owns TwiML, AWS owns the S3 API, Cloudflare owns Workers.

Lean into the protocol framing. This is the business pitch — Plivo has been a great CPaaS but doesn't OWN a developer standard. AVIP-0 is the wedge. Spec is free, broker infrastructure is the product. Compare to TwiML: Twilio's secret weapon for 15 years has been that every webhook in voice apps speaks TwiML. Even Plivo speaks TwiML syntax for compat. That's an enormous moat. AVIP-0 can be the same.

The roadmap. The key data point: AVIP-1 was verified 2 hours ago via the probe at /api/trigger-dial-probe — we sent "90901234#" via Plivo's sendDTMF event on one leg and observed all 9 digits arrive on the peer leg's stream. The Dial bridge carries DTMF end-to-end. AVIP-2 is the headline UX upgrade — humans don't hear the handshake. Done via SIP custom headers during call setup (before any TTS plays) plus the "polite cover" pattern where DTMF nonce is mixed under a normal greeting at -20dB. AVIP-4 is the long arc — agents call agents over WebSocket without burning PSTN at all. Phone networks become the human-fallback layer.
