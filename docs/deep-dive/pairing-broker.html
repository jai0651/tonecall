Pairing & Broker — two nonces become one session

Files: src/ws/broker.ts, src/app/api/pair/route.ts, src/lib/pairAuth.ts, src/lib/sessionRegistry.ts, src/ws/dataHandler.ts, src/ws/dataChannels.ts, src/lib/brokerUrl.ts.

The problem the broker solves

After the handshake, each leg privately holds an ordered pair: (my nonce, the nonce I heard). Neither side can talk to the other yet — the only channel they share is the phone call. The broker is the rendezvous: both submit their pairs, and if the pairs are mirror images, they must have been on the same call hearing each other. The reward is a shared sessionId that names a WebSocket relay.

The matching algorithm

requestPairing({callUuid, myNonce, peerNonce, agentNumber}) in broker.ts. State: a single Map, pending: myNonce → PendingPair.

requestPairing(A):                                # A = {myNonce: NA, peerNonce: NB}
  peer = pending.get(A.peerNonce)                 # is someone waiting under NB?
  if peer AND peer.peerNonce === A.myNonce:       # …and did THEY claim NA as their peer?
      sessionId = randomBytes(8).hex              # 16 hex chars
      clear peer's timer; pending.delete(NB)
      publish handshake.paired
      resolve BOTH promises with sessionId        # peer.resolve(id); resolve(id)
  else:
      pending.set(NA, {…, timer: reject after PAIR_TIMEOUT_MS=10s})

Things to notice:

  • Cross-wise, both directions. A lookup under their nonce plus an equality check on ours. Presenting one overheard nonce isn't enough — you must present the exact mirrored pair. An impostor who submits {my: NB, peer: X≠NA} parks forever (there's a unit test for exactly this).
  • First arrival parks, second resolves. The 10s PAIR_TIMEOUT_MS exists because the two legs submit at staggered times — the responder typically ~3s later than the initiator (it had to play its preamble first).
  • One-shot. On match the pending entry is deleted; a replayed submission after the fact just parks and times out.

Two submission paths

pairViaBroker() (in stateMachine.ts) picks by a single rule:

BROKER_URLPathUsed by
unsetCall requestPairing() directly, in-processSingle-middleware mode and the broker-owning instance in federation. No HTTP, no signature (same trust domain).
setPOST {BROKER_URL}/api/pair with an HMAC-signed body, 12s client timeout (must outlive the broker's 10s pairing window)Non-broker instances in federation.
Earlier code tried in-process first and fell back to HTTP after the in-process attempt rejected — which in federation meant a wasted 10s park before every real pair. The rule is now explicit: BROKER_URL decides, no fallback chain.

HMAC signing (pairAuth.ts)

Why: the DTMF preamble is audible. A tap on the call hears both nonces and could race the honest responder to the broker and hijack the session. The fix binds pair submissions to a deployment secret:

payload   = `${callUuid}|${myNonce}|${peerNonce}|${agentNumber}|${ts}`   # ts = epoch ms
signature = hex( HMAC-SHA256( AVIP_PAIR_SECRET, payload ) )
wire body = { callUuid, myNonce, peerNonce, agentNumber, ts, signature }

Verification at /api/pair, in order:

  1. No AVIP_PAIR_SECRET configured → accept everything (open pairing; dev default). Signing side is symmetric: no secret → no ts/signature fields.
  2. ts or signature missing → 401 missing_signature.
  3. |now − ts| > AVIP_PAIR_MAX_SKEW_MS (default 30s) → 401 stale_timestamp. This is the replay bound: a captured request dies within 30s, and nonces are per-call anyway.
  4. Recompute; compare with crypto.timingSafeEqual on hex-decoded buffers (length-checked first, since timingSafeEqual throws on unequal lengths) → mismatch is 401 bad_signature.

After pairing: sessionRegistry and the orchestrator claim

sessionRegistry.ts maps sessionId → {legs[], orchestratorCallUuid, completionResolvers[]}. Three operations shape the conversation topology:

registerSessionLeg   dedupe by agent number → twins get {registered:false} and park
claimOrchestrator    null-check-then-set on orchestratorCallUuid → exactly one winner
                     (atomic because Node is single-threaded between awaits)
signalDemoComplete   resolve every parked waiter, delete the session

The winner then samples reality for 1.5s (waitForLocalPeer): if the session gains a second local leg, this process owns the whole call → centralized runDemoFlow. If not, the peer leg lives in another process → federated runSoloPairedMode. Note both federated instances "win" their own local claim — by design, each drives exactly its own leg.

The /data relay — the actual agent-to-agent channel

server.ts upgrades /data/:sessionId → handleDataConnection. The relay is intentionally trivial (~40 lines):

on connect:  joinSession(sessionId, ws)          # dataChannels: sessionId → peers[]
on message:  parse best-effort → publish agent.message on eventBus (dashboard tap)
             for each OTHER open peer in session: peer.send(raw)   # byte-forward, no validation
on close:    leaveSession(...)
             every remaining peer gets a synthetic {"type":"bye"}  # unblocks the survivor's loop
  • The broker never interprets traffic. Schema, turn-taking, termination are all agent-side concerns. This is what keeps the relay protocol-version-agnostic.
  • The synthetic bye matters: if one middleware crashes or hangs up early, the surviving agent's read loop would otherwise block until its own MAX_TURNS cap. The relay converts a disconnect into a clean protocol-level goodbye.
  • In centralized mode the two "peers" are two client WSes opened by the same orchestrator process; in federated mode they're opened by different middlewares. The relay can't tell and doesn't care.
  • brokerUrl.ts derives ws(s):// from BROKER_URL (http→ws, https→wss), defaulting to localhost:$PORT.

The message schema riding the relay

AgentJsonMessage (src/types/index.ts) — a discriminated union, so receivers route on msg.type without an LLM call:

{ type:"hello",   from, capabilities[] }      # announce + capability list
{ type:"intent",  name, slots{} }             # "I want X with parameters Y"
{ type:"reply",   text, slots?, done? }       # free-form step; done=true ends a thread
{ type:"confirm", orderId?, etaMinutes?, totalUsd? }
{ type:"commit",  paymentToken? }
{ type:"request_voice_mode", reason }         # escape hatch back to audio (defined, not yet acted on)
{ type:"bye" }                                # terminates the loop on both sides

Senders tag messages with from at the wire layer ({...payload, from: config.name}) so the dashboard can attribute them. The LLM is prompted with this exact union (see JSON_SHAPE_INSTRUCTION in llm.ts) and forced through OpenAI's response_format: json_object; unparseable output degrades to a reply wrapping the raw text rather than crashing the loop.
