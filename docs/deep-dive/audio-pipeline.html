Audio Pipeline — every byte on the voice wire

Files: src/lib/audio.ts, src/lib/audioCodec.ts, src/lib/tts.ts, src/lib/stt.ts, src/ws/voiceTurn.ts, src/ws/voiceMode.ts, src/lib/plivo.ts.

The Plivo Stream WebSocket — wire protocol

Declared by the answer XML: <Stream keepCallAlive="true" bidirectional="true" audioTrack="inbound" contentType="audio/x-mulaw;rate=8000">wss://…/voice/<callUuid></Stream>. Plivo then connects to us (we are the WS server). Constraint to memorize: bidirectional="true" forces audioTrack="inbound" — we hear what the far side sends, and can inject audio toward our side's speaker. Across a Dial bridge that's exactly symmetric: my playAudio = your inbound.

Framing arithmetic

8000 samples/sec × 1 byte/sample (μ-law) = 8000 B/s
FRAME_BYTES        = 160  → 160/8000 = 20ms per frame  (FRAME_DURATION_MS)
1 second of speech = 50 frames = 8 KB raw ≈ 10.7 KB base64
speak() chunk      = 1600 B = 200ms   (10 frames per playAudio payload)

chunkToFrames() iterates a buffer in 160-byte steps and pads the tail with 0xFF — which is μ-law for "sample value 0", i.e. digital silence; zero-padding would be a loud DC click.

G.711 μ-law — the codec, actually explained

Telephony's 8-bit logarithmic encoding (ITU-T G.711). Human hearing is logarithmic, so μ-law spends its 8 bits where ears care: fine resolution near silence, coarse near peaks. audioCodec.ts implements it from scratch — no dependencies:

encode(pcm16):                                  decode(byte):
  sign = top bit; pcm = |pcm|                     invert byte (μ-law stores inverted)
  clip at 32635; add BIAS 0x84                    exponent = bits 4-6, mantissa = bits 0-3
  exponent = position of highest set bit (0-7)    sample = ((mantissa<<3)+0x84) << exponent, − 0x84
  mantissa = next 4 bits below it                 re-apply sign
  byte = ~(sign | exponent<<4 | mantissa)

Effectively a tiny hardware-friendly float: 1 sign bit, 3 exponent bits, 4 mantissa bits. The rest of the codec file: linear-interpolation upsampling and window-averaging downsampling (resamplePcm16), and a minimal 44-byte-header WAV writer (pcm16ToWav) used for Whisper uploads and debug recordings. Quality target is explicitly "telephony, not studio" — no anti-alias filtering, which is fine for an 8kHz endpoint.

Text → speech: the speak() path

speak() (src/ws/voiceTurn.ts) is the only way conversation code touches audio:

speak({ws, speakerName, text, voice, waitForDuration=true, tailMs=150})
 1. publish voice.transcript FIRST        # dashboard shows the line before audio exists
 2. tts.synthesize({text, voice})         # → Buffer of μ-law 8kHz
 3. ws.send(playAudioFrame(chunk)) per 1600B chunk, no pacing
    # Plivo buffers; pacing only matters if you want to interrupt mid-utterance
 4. if waitForDuration: sleep(audio.length / 8000 × 1000 + tailMs)
    # SENDING is instant; this sleep models PLAYBACK so callers can sequence turns

That step-4 sleep is the whole turn-taking mechanism in centralized mode: the orchestrator awaits each speak(), so agents never talk over each other.

Inside tts.synthesize (real variant): OpenAI tts-1 with response_format:'pcm' → mono PCM16 @ 24kHz → resamplePcm16(24000→8000) → pcm16ToMulaw. First-byte latency ~300–600ms. Side effects, both optional: RECORD_AUDIO=true writes each utterance as a 24kHz WAV under ./tonecall_audio/; PLAY_LOCAL=true pipes it to afplay/aplay so the operator hears the call live. Stub variant emits 1s of μ-law silence with a few marker bytes.

Speech → text: the STT path (human mode only)

openStt() returns a stateful stream. Whisper is a batch API, so "streaming" is really silence-gated batching:

feed(160B frame):
  append to buffer
  compute silenceFraction(frame)            # fraction of samples near μ-law zero
  if buffered speech ≥ ~1.4s AND trailing silence ≥ ~500ms:
      mulawToPcm16 → resample 8k→16k → pcm16ToWav → whisper-1 /audio/transcriptions
      return transcript (or null if the chunk was effectively silence)
  else return null

Consequence: end-of-utterance detection adds ~500ms minimum latency, and there is no barge-in — the agent finishes speaking regardless. The header comment says the honest thing: this path exists to demonstrate the slow lane that the data channel replaces; swapping to a realtime STT API is an upgrade, not a redesign.

The human voice loop, assembled

runVoiceMode (src/ws/voiceMode.ts):
  publish phase.started(human_voice)
  speak(greeting)                     # persona-fixed line, the one scripted string in the flow
  for each media event:
      stt.feed(frame) → transcript?  → publish voice.transcript(caller)
      llm.respondText(persona, history, transcript)
      speak(reply)                    # 20ms-paced frame sends here (interruptible-ish)
  until stop event or WS close
  stt.close(); publish phase.ended; REST hangup

Note the asymmetry: voiceMode's private speak paces frames at 20ms intervals (so a hangup mid-reply stops promptly), while voiceTurn.speak() burst-sends and sleeps. Two implementations, two trade-offs; both end up as the same playAudio wire frames.

  whisper batch          0.3–1s           ────────────────────────
  llm.respondText        0.5–2s           total               ~0.5–2s
  tts first byte         0.3–0.6s
  reply playout          2–4s
  ────────────────────────────

The demo.summary metrics (demoFlow.publishSummary) monetize this: voice seconds are billed at a blended $0.0035/s (PSTN+STT+LLM+TTS), data seconds at $0.0008/s (LLM only), and the counterfactual baseline is dataTurns × this call's observed voice sec/turn — an estimate derived from the same call, not a canned number (falls back to 4s/turn only if zero voice turns were observed).
