Federation — two middlewares, one deal

The default demo topology: each agent runs on its own process, and the ONLY things the processes share are (1) the phone call between their DIDs, (2) the broker URL, (3) the pair secret. Files: src/lib/agentConfigs.ts (AGENT_OWNED), src/ws/pairedMode.ts, src/lib/eventBus.ts, src/app/api/forward-event/route.ts, src/app/api/simulate*/….

Why this is the default (and why it matters)

In single-process mode, one orchestrator (demoFlow.ts) scripts both agents — great for metrics, but structurally it's one program talking to itself. Federation is the honest claim: two independent runtimes that cannot cheat through shared memory discover each other purely over the call (DTMF preamble) and coordinate purely over the wire (broker HTTP + data relay). Everything cross-vendor AVIP promises is exercised by this topology; a Twilio-side implementation would slot in where instance B sits, changing nothing on instance A.

Solo paired mode — distributed turn-taking without coordination

runSoloPairedMode({ws, callUuid, config, sessionId, role}). The initiator/responder role — already agreed via topology — sequences everything; there is no other synchronization:

INITIATOR                                     RESPONDER
─────────                                     ─────────
open data WS to broker                        open data WS to broker
speak LLM intro on own leg  ──audio bridge──▶ (hears it; doesn't parse it)
send {hello, capabilities}  ──data relay────▶ first peer message arrives:
                                                1. speak own LLM intro   ◀── audio
                                                2. llm.respondJson(hello) → reply
reply arrives → respondJson → …               … alternating, MAX_TURNS=12 cap …
                       either side emits {type:"bye"} (or reply.done=true)
speak LLM goodbye (summarizes JSON history)   speak LLM goodbye
REST hangup own leg                           REST hangup own leg
  • Only the initiator opens with hello. The old version had both sides fire hellos, producing two interleaved conversations. One opener + respond-on-receive = strict alternation with zero cross-process locking.
  • Intros can't overlap: the responder speaks its intro only upon the first data message, which the initiator sends after finishing its own intro (speak() blocks for playout duration).
  • Goodbyes are grounded: each side prompts llm.respondText with the last 10 JSON messages, so the spoken summary reflects the actual outcome ("Order confirmed, six AM delivery…"), with a hardcoded line only as exception fallback.
  • Failure containment: an AbortController tied to both sockets stops the loop if either closes; the data relay's synthetic bye (see Pairing) unblocks the survivor if the peer process dies; the 12-turn cap bounds a runaway LLM.
  • The cosmetic "modem chirp" audio from the hackathon build is gone here — on a real bridge the peer would actually hear it over the intros.

The simulators — testing all of this without a phone bill

Both fake exactly one thing: Plivo. They open client WSes to /voice/:callUuid and shuttle each leg's outbound sendDTMF to the other leg as inbound dtmf events — byte-for-byte what the Dial bridge does. Everything downstream (handshake, roles, broker, HMAC, paired mode, events) is the production code path.

Federation limits (current, known)

  • The broker is a role, not a service — instance A is a single point of failure for pairing and the data relay. Fine for two parties; a real deployment splits the broker out (or replaces it with the roadmap's /.well-known direct-WSS discovery).
  • Shared-secret trust — see the threat table on the Pairing page.
  • The trigger is asymmetric — only the instance owning the originating agent can start a call. B can equally trigger toward A; there's just no "third party asks both to talk" flow yet.
  • Event forwarding is lossy by design — fire-and-forget POSTs; a dropped event means a gap on the leader dashboard, never a broken call.
