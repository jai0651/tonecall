The Handshake — in-band DTMF, symbol by symbol

Files: src/lib/dtmf.ts (grammar + detector), src/ws/stateMachine.ts (runInBandNonceHandshake), src/lib/dtmfBus.ts, src/lib/dialRegistry.ts (roles).

Why DTMF at all

The handshake signal must survive whatever sits between two arbitrary phone endpoints: codecs, carriers, transcoding, cross-vendor bridges. DTMF (the touch-tone signal) is the one thing the entire phone network has treated as sacred for 50 years — IVRs depend on it, so every hop either passes the tones through or re-encodes them as RFC 2833 signaling events. Plivo surfaces received DTMF as clean JSON dtmf events on the Stream WS, and lets us inject it with a sendDTMF WS event. We never touch raw tones.

The grammar

preamble := "9090" nonce "#"
nonce    := 8 decimal digits, zero-padded    (e.g. 00734921)

full example:   9 0 9 0 6 1 0 4 5 1 0 0 #     (13 DTMF symbols)
PartWhy exactly this
9090Protocol magic + version marker. Digits only — Plivo's DTMF detector drops * more often than digits, so the classic "*-prefixed" style was rejected. Chosen to be something no human dials as the first thing on a call.
8-digit nonceIdentifies this leg for this handshake. 108 space → a human randomly mashing a keypad has a 10-8 chance of forging a specific valid nonce, and would additionally need the 9090 prefix and the # terminator around it. Generated with Math.random() deliberately: nonces prove co-presence on the call, not identity — identity is the HMAC layer at pairing.
#End marker, reliably detected across PSTN equipment. Lets the detector know the nonce is complete without length-prefix tricks.

At typical 200ms tone + 100ms gap pacing, 13 symbols ≈ 3.9 seconds of playout. That number drives every timeout below.

Roles come from topology, not names

Earlier builds broke ties alphabetically by agent name — which collapses in federation, where each middleware only knows its own agent (both sides would elect themselves initiator). Now the role is a fact about the call:

RoleWho gets itRecorded where
initiatorThe leg whose answer webhook claimed a pending dial — i.e. the leg that returned <Dial> XML. (Simulator legs get it via markDialInitiator().)dialRegistry: roleByCallUuid.set(callUuid,'initiator') inside claimDialTarget
responderEveryone else: the dialed-into peer DID, a human's inbound call, an unknown caller. It's the absence of an entry — getDialRole() defaults to responder.(no entry)
The UX consequence: a responder never emits first. So a human calling one of our DIDs hears silence (then a greeting), never unsolicited beeping. Only the side that placed the call announces itself — and it placed the call on purpose.

runInBandNonceHandshake — the actual machine

One promise per leg, resolved by the first of three outcomes: success ({myNonce, peerNonce, peerNonceAt}), timeout (null), or WS close (null). Internals:

state:  resolved=false   hasEmitted=false   peerNonce=null
wiring: dtmfBus.subscribe(agentNumber, digit → detector.feed)
        ws.once('close', fail)
timers: INITIATOR only → initialTimer  = setTimeout(fireEmit, 500ms)
                         emitTimer     = setInterval(fireEmit, PREAMBLE_INTERVAL_MS=4s)
        both roles     → timeoutTimer  = setTimeout(fail, windowMs)

fireEmit():        ws.send({event:"sendDTMF", dtmf:"9090<myNonce>#"}); hasEmitted=true; succeed()
on detected nonce: if nonce !== myNonce → peerNonce=nonce
                   if !hasEmitted → fireEmit()      // responder answers NOW
                   succeed()
succeed():         only fires when hasEmitted AND peerNonce   // both directions done

Success therefore means: we played our preamble AND we decoded theirs. That two-sided requirement is what makes the subsequent broker submission cross-consistent.

Timing windows and why

ConstantValue (env)Reasoning
INITIATOR_FIRST_EMIT_MS500msEmit almost immediately after our stream opens. On real calls this first burst is usually wasted — the Dial is still ringing, there's no bridge to carry it — and that's fine.
REEMIT_INTERVAL_MS4s (PREAMBLE_INTERVAL_MS)Must exceed the ~3.9s playout so consecutive preambles never overlap themselves. Repetition is the loss-recovery mechanism: whichever burst lands after the bridge exists gets through.
initiator window20s (INITIATOR_HANDSHAKE_TIMEOUT_MS)Dial ring time (up to several seconds, timeout="30" on the Dial itself) + preamble playout + responder's answering preamble + margin. Roughly 4 emit cycles.
responder window8s (HANDSHAKE_TIMEOUT_MS)The responder's stream only exists once the bridge is already up, and an initiator's preamble lands within ~1–4.5s of that (first-or-second burst). 8s ≈ 2× worst case. It is also exactly how long a silent human waits before the greeting — the protocol tax on humans.

PreambleDetector — the decoder

A deliberately dumb streaming matcher (src/lib/dtmf.ts):

feed(digit):
  buffer += digit
  if buffer.length > 64: buffer = buffer.slice(-64)   // bound memory; 64 ≈ 2 overlapping bursts
  m = /9090(\d{8})#/.exec(buffer)
  if m: buffer = ''; return m[1]                       // reset → a repeated preamble re-detects
  return null

Properties that matter:

  • Split-tolerant: digits arrive one per dtmf event; the buffer reassembles across events, so pacing/jitter is irrelevant.
  • Garbage-tolerant: leading/trailing junk digits don't matter; the regex finds the pattern anywhere in the window.
  • Self-filtering: the caller compares the detected nonce against myNonce — if some path echoes our own preamble back (a misbehaving bridge), we ignore it rather than "pairing with ourselves".
  • Duplicate-emission safe: Plivo occasionally double-fires a tone; the 64-char window plus reset-on-match keeps that harmless.

The twin-leg problem and dtmfBus

Plivo sometimes books two call_uuids for one PSTN leg and opens a Stream WS for each. Two consequences the code handles explicitly:

  1. Only one handshake per number. runStateMachine takes a per-agent-number lock (handshakeInProgress Map). The twin's WS parks until close. Without this, both twins would handshake and then fight over the orchestrator claim.
  2. DTMF may arrive on the "wrong" twin. Empirically the dtmf events fire on one specific twin — not necessarily the one holding the lock. Hence the dtmfBus: every twin's voiceHandler publishes every dtmf digit onto a per-number EventEmitter channel, and the (single) handshake subscribes to the number, not the socket. Fan-in solves the ambiguity.
twin WS #1 (lock holder) ── digits? ──▶ ┌────────────────┐
                                        │ dtmfBus[number] │ ──▶ handshake detector
twin WS #2 (parked)      ── digits? ──▶ └────────────────┘

Security posture of this layer

The preamble is audible and public — anyone on the call path can hear both nonces. The handshake therefore only ever proves "someone on this call speaks AVIP". Session integrity comes from the next layer: the broker requires cross-wise knowledge (you must present the peer's nonce as well as your own), and with AVIP_PAIR_SECRET set, an HMAC that an eavesdropper without the deployment secret can't forge. See Pairing & Broker for the exact construction and the residual gaps.
