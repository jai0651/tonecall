State & Registries — the Maps under everything

All runtime state is in-memory, keyed on globalThis. This page catalogs every store: shape, writers, readers, lifetime.

Why globalThis (the trick that keeps recurring)

The process runs two module graphs: Next.js compiles API-route modules on its own, while server.ts (tsx) imports the WS handlers through a second graph. A plain module-scope const map = new Map() would therefore exist twice — the answer webhook would write into one copy and the voice handler would read the other, and nothing would ever pair. Every store instead does:

const G = globalThis as unknown as { __tonecall_call_registry?: Map<string,string> };
const map = (G.__tonecall_call_registry ??= new Map());

globalThis is per-process, so both graphs converge on one instance. The ??= also makes hot-reload in dev safe: re-evaluated modules reattach to the surviving Map rather than dropping live calls.

Catalog

1 · callRegistry — src/lib/callRegistry.ts

Shape__tonecall_call_registry: Map<callUuid, agentNumber>
Written by/api/answer (real calls), /api/simulate + /api/simulate-register (fake calls)
Read byvoiceHandler — the WS URL only carries a callUuid; this Map answers "whose call is this?". The handler polls up to 1s because the webhook and the WS upgrade race.
LifetimeDeleted in voiceHandler's finally (unregisterCall).

2 · dialRegistry — src/lib/dialRegistry.ts

Shape__tonecall_pending_dials: Map<agentNumber, {target, expiresAt, claimedByCallUuid}>
__tonecall_dial_roles: Map<callUuid, 'initiator'|'responder'> (responder = absent)
Written bytrigger-call (setPendingDial, 60s TTL), answer (claimDialTarget), simulators (markDialInitiator)
Read byanswer (role → which XML), stateMachine (role → emit behaviour + timeout window)
SemanticsClaim is idempotent per callUuid (webhook retry ⇒ same XML) and exclusive across callUuids (twin leg ⇒ null ⇒ callee XML ⇒ never a second <Dial>). Numbers normalized to +-prefixed E.164 on the way in.
LifetimePending: TTL. Roles: cleared in voiceHandler teardown (clearDialRole).

3 · broker pending pairs — src/ws/broker.ts

Shape__tonecall_pending_pairs: Map<myNonce, {callUuid, myNonce, peerNonce, agentNumber, resolve, reject, timer}>
__tonecall_sessions_for_nonces: Map<"n1:n2" (sorted), sessionId> (audit trail of matches)
Written/read byrequestPairing only — see Pairing for the algorithm
LifetimeEntry deleted on match or by its own 10s timer (which rejects the parked promise).
NoteThe Map stores live resolve functions — the broker resolves the first submitter's promise from inside the second submitter's call. Promises-as-rendezvous, not polling.

4 · sessionRegistry — src/lib/sessionRegistry.ts

Shape__tonecall_sessions: Map<sessionId, {legs: [{callUuid, config, ws}], orchestratorCallUuid, completionResolvers[]}>
Written bystateMachine after pairing (registerSessionLeg, claimOrchestrator); demoFlow at the end (signalDemoComplete)
Read bydemoFlow (needs both legs' WSes + configs), stateMachine.waitForLocalPeer (centralized-vs-federated decision)
SemanticsLeg dedupe by agent number (twin protection #3). Orchestrator claim = null-check-then-set — atomic because Node runs the check and set in one synchronous slice. waitForDemoComplete parks losers on a resolver list and on their own WS close (whichever first).
LifetimeDeleted by signalDemoComplete. In federated solo mode sessions are never explicitly completed — legs exit when sockets close; the entry leaks until restart (known wart, harmless at demo scale).

5 · dataChannels — src/ws/dataChannels.ts

Shape__tonecall_data_sessions: Map<sessionId, {peers: WebSocket[]}>
Written/read bydataHandler (join on connect, leave on close, iterate peers per message)
LifetimeSession entry auto-deletes when the last peer leaves. No cap on peers — a third connector would silently join the relay (open pairing caveat; the HMAC layer protects session creation, not relay attachment).

6 · dtmfBus + eventBus — src/lib/dtmfBus.ts, src/lib/eventBus.ts

ShapeNot Maps — two EventEmitter singletons on globalThis (__tonecall_dtmf_bus, __tonecall_event_bus), maxListeners=100.
dtmfBusChannel per agent number. Publishers: every voiceHandler (all twins). Subscriber: the one running handshake. This fan-in is twin protection #2 — see Handshake.
eventBusSingle demo channel carrying DemoEvents. Publishers: everything. Subscribers: the SSE route (per connected dashboard). publishDemo additionally fire-and-forget POSTs to FORWARD_EVENTS_TO/api/forward-event if set; the receiving side re-emits via publishLocal which never forwards — the loop-prevention invariant.

7 · handshake lock + live players — src/ws/stateMachine.ts, voiceHandler.ts

handshake lock__tonecall_handshake_lock: Map<agentNumber, callUuid>. First WS per number runs the state machine; twins park until their socket closes (twin protection #1). Released in a finally guarded by "am I still the holder?" so a parked twin can't clear the winner's lock.
live players__tonecall_live_players: Map<number, {proc, refs}> — refcounted sox play subprocesses for AVIP_PLAY=1, so twins don't double the audio.

The three twin defenses, side by side

Plivo's twin call_uuids threaten three different stages; each has its own guard because they trigger at different times:

#GuardStagePrevents
1handshake lock (per number)WS opentwo concurrent handshakes for one agent
2dtmfBus fan-in (per number)during handshakeDTMF landing on the twin the lock-holder isn't reading
3session leg dedupe (per number) + dial claim (per callUuid)post-pairing / answertwin joining the session or triggering a second Dial

What a process restart loses

lost:  every in-flight call registration, dial role, pending pair,
       session, data relay membership, SSE subscription
kept:  nothing (there is no disk/Redis persistence)

symptom on restart mid-call: Plivo's Stream WS reconnects? No — the socket
drops; keepCallAlive keeps the CALL up until <Wait> expires or Plivo times
the stream out, but the middleware no longer knows the callUuid → the leg
is orphaned until hangup/timeout.
Production note. Every store on this page is a Map interface with narrow functions in front of it — registerCall/lookup/unregister, setPendingDial/claim, etc. Swapping the backing store for Redis (with TTLs mapping to the existing expiry semantics) changes no call-flow code. That's the intended migration path; it just isn't built.
