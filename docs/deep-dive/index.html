Tonecall / AVIP-1 — the granular deep dive

How every moving part works, at the level of individual webhooks, WebSocket frames, timers, and Map entries. Written against the current (post-Conference) codebase.

Reading contract. Every claim on these pages maps to a file and usually a specific function. File paths are relative to the repo root. If a page and the code ever disagree, the code wins — update the page.

What this system is, in one paragraph

Tonecall is a middleware that sits between your CPaaS provider (telephony) and OpenAI (LLM + STT + TTS). It answers phone calls on behalf of AI agents. When the thing on the other end of the call is another AVIP agent, the two sides recognise each other with a DTMF handshake played over the call itself, pair through a broker, and move the actual negotiation to a JSON WebSocket — keeping the voice line open for humans and for spoken bookends. When the other end is a human, the agent behaves like any phone AI: speech-to-text → LLM → text-to-speech.

Each page of this set owns one or two layers. The layers only talk through narrow interfaces: the topology layer hands the handshake a role; the handshake hands pairing a nonce pair; pairing hands the conversation a sessionId; the conversation only touches transport through speak() and the data WS.

Glossary you need on every page

TermMeaning here
DIDA phone number we own on our CPaaS provider. Two agent DIDs (PLIVO_NUMBER_A/B) + one caller-ID DID.
legOne call between the provider and an endpoint. An A↔B bridged call has two legs; each leg gets its own answer webhook, its own callUuid(s), and its own Stream WS.
twinThe provider sometimes books TWO call_uuids for one PSTN leg and opens a Stream WS for each. Dedup logic exists in three places (handshake lock, session registry, dial claim).
initiator / responderHandshake roles derived from topology: the leg that <Dial>ed out emits the preamble proactively; everyone else answers only after hearing one.
nonce8 random digits identifying one leg for one handshake. Proof of co-presence, not a secret.
sessionId16 hex chars minted by the broker when two nonce submissions cross-match. Names the /data/:sessionId relay.
inbound / outbound (audio)Relative to a leg: inbound = audio arriving FROM the far side; outbound = audio we inject TOWARD the far side. Our Streams read inbound; playAudio/sendDTMF write outbound. Across a Dial bridge, one leg's outbound becomes the other leg's inbound — that's the whole trick.
