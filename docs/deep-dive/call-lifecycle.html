Call Lifecycle — one A↔A call, end to end

Single-middleware wording for brevity; the Federation page shows which steps move to the second process (spoiler: the flow is identical, only the webhook destinations differ).

The cast

vegetable_vendor  = DID A (PLIVO_NUMBER_A), persona "Anil, Mumbai Fresh Produce"
pizza_shop        = DID B (PLIVO_NUMBER_B), persona "Bella Pizza procurement"
caller-ID DID     = PLIVO_CALLER_ID (only used as the `from` of the originate)
middleware        = this Next.js + ws process, reachable at PUBLIC_HOST

Timeline at a glance

t≈0.0s   POST /api/trigger-call            (dashboard button)
t≈0.1s   Provider REST originate → DID A rings
t≈1–2s   DID A answers → POST /api/answer  (leg A)  → XML: Stream + Dial B
t≈2s     wss /voice/<callA> opens          (leg A stream live)
t≈2.5s   leg A emits DTMF preamble #1      (usually lost — B still ringing)
t≈3–6s   Dial connects → POST /api/answer  (leg B)  → XML: Stream + Wait
t≈6s     wss /voice/<callB> opens          (bridge is now end-to-end)
t≈6.5s   leg A re-emits preamble           (REEMIT_INTERVAL_MS = 4s cadence)
t≈7–10s  B hears A's preamble → emits its own → both submit nonces
t≈10s    broker matches → sessionId        (pairing done)
t≈10s+   conversation phases (intro → JSON → goodbye)
t≈40–80s REST hangup per leg → call.ended
Dashboard → middleware

Step 1 — The trigger

Dashboard.tsx POSTs /api/trigger-call with an empty JSON body. The route (src/app/api/trigger-call/route.ts) resolves:

numberA  = body.numberA ?? listAgentConfigs()[0].number ?? PLIVO_NUMBER_A   // must be OWNED locally
numberB  = body.numberB ?? PLIVO_NUMBER_B                                   // may live anywhere
callerId = body.callerId ?? PLIVO_CALLER_ID ?? numberA

Guard: if getAgentConfig(numberA) is undefined (this middleware doesn't own it — e.g. wrong instance in federated mode) → 400 numberA_not_owned. Then two things happen, in order:

  1. setPendingDial(numberA, numberB) — writes the intent "when numberA answers, Dial numberB" into the dialRegistry (60s TTL).
  2. plivoClient.originate({from: callerId, to: numberA, answerUrl, accountId:'1'}) — ONE outbound call. The answerUrl parameter is passed but effectively ignored: when the destination of an originate is a same-account DID with an Application attached, the provider runs the Application's answer URL instead.

Response to the dashboard: {ok, mode:'dial_bridge', originator:{to, dialTarget, requestUuid}}. A call.triggered event goes out on the eventBus.

Provider → middleware (leg A)

Step 2 — Answer webhook, initiator leg

DID A "answers" (its Application does), and the provider POSTs form-encoded data to /api/answer:

CallUUID=aaaa-1111-…   From=+1CCCCCCCCCC (caller-ID)   To=+1AAAAAAAAAA (DID A)   …

The handler (src/app/api/answer/route.ts) walks through:

  1. Number normalization — bare digits get a + prefix so registry keys are stable.
  2. Agent identification — try getAgentConfig(to) first (inbound direction), then getAgentConfig(from) (outbound direction). Here to = DID A → agent vegetable_vendor. Neither matches → 404 (call to a number we don't run).
  3. registerCall(callUuid, agentNumber) — so the voice WS (which only knows the callUuid from its URL) can find the agent later.
  4. Role decision — claimDialTarget(agentNumber, callUuid). The pending dial from step 1 exists and is unclaimed → this callUuid claims it, gets back numberB, and is recorded as initiator. (A webhook retry with the same callUuid gets the same answer — idempotent. A twin callUuid for the same number gets null — no second Dial, ever.)
  5. XML — buildAnswerXml({role:'dial_originator', …}):
<?xml version="1.0" encoding="UTF-8"?>
<Response>
<Stream keepCallAlive="true" bidirectional="true" audioTrack="inbound"
        contentType="audio/x-mulaw;rate=8000">wss://PUBLIC_HOST/voice/aaaa-1111-…</Stream>
<Dial timeout="30" callerId="+1AAAAAAAAAA"><Number>+1BBBBBBBBBB</Number></Dial>
</Response>

Order matters: <Stream> executes first so our WS is attached before the Dial starts ringing B — we must be listening before the bridge exists. The Dial's callerId is DID A itself, so leg B's webhook sees From=+1AAAAAAAAAA: a stable, meaningful identity.

Provider → middleware (leg B)

Step 3 — Answer webhook, responder leg

The <Dial> rings DID B. DID B's Application fires its answer URL (same route in single-middleware mode; the peer middleware in federation):

CallUUID=bbbb-2222-…   From=+1AAAAAAAAAA   To=+1BBBBBBBBBB

Same handler, but now claimDialTarget returns null (no pending dial for DID B) → role callee:

<Response>
<Stream keepCallAlive="true" bidirectional="true" audioTrack="inbound"
        contentType="audio/x-mulaw;rate=8000">wss://PUBLIC_HOST/voice/bbbb-2222-…</Stream>
<Wait length="600"/>
</Response>

The <Wait> is the load-bearing fix: the hackathon build returned <Conference> here, which yanked the leg into a mixer and broke the Dial bridge (the historical "same-account Dial hits Ring Timeout" mystery). With <Wait>, answering completes the Dial and the provider bridges the legs: leg A's outbound audio is now leg B's inbound audio, and vice versa. A human dialing DID B directly gets this exact same XML — the callee leg makes no assumptions about who's calling.

Provider → middleware (both legs)

Step 4 — Voice WebSockets connect

server.ts catches the HTTP upgrade, matches /^\/voice\/([^/]+)$/, and hands the socket to handleVoiceConnection(ws, callUuid) (src/ws/voiceHandler.ts), which per leg:

  1. Polls lookupNumberForCall(callUuid) for up to 1s (the webhook and the WS race; the webhook usually wins but not always).
  2. Resolves the AgentConfig; publishes handshake.started.
  3. Installs the message tap: dtmf events → dtmfBus.publish(number, digit, callUuid); media events → optional debug capture (AVIP_CAPTURE=1) / live playback (AVIP_PLAY=1).
  4. Calls runStateMachine({ws, callUuid, config}) and, when it returns, unregisters the call, clears the dial role, closes the WS, publishes call.ended.
middleware (per leg)

Step 5 — Handshake

Covered in full on the Handshake page. Summary: getDialRole(callUuid) says leg A is initiator (20s window, emits 9090<nonceA># at 0.5s then every 4s) and leg B is responder (8s window, silent until it hears a preamble, then answers with 9090<nonceB>#). Each side ends up holding {myNonce, peerNonce} — or null on timeout, which routes to runVoiceMode (the human path, step 9).

middleware ↔ broker

Step 6 — Pairing

Covered on the Pairing page. Each leg submits {callUuid, myNonce, peerNonce, agentNumber} — in-process if BROKER_URL is unset, HMAC-signed HTTP POST to /api/pair otherwise. Cross-matching submissions mint one 16-hex sessionId; both submitters get it. Events: call.mode=agent_to_agent, handshake.peer_detected, handshake.paired, pairing.summary(path=in_band_nonce).

middleware (per leg)

Step 7 — Who drives the conversation?

Each leg calls registerSessionLeg(sessionId, leg). Duplicate agent number in the same session (a twin that slipped through) → not registered → parks on waitForDemoComplete. Then exactly one leg wins claimOrchestrator(sessionId, callUuid) (a plain null-check-then-set; single-threaded JS makes it atomic) and checks: does the session have 2 local legs within 1.5s?

Both legs local?PathMeaning
yesrunDemoFlow (demoFlow.ts)Single-process mode: one orchestrator scripts BOTH sides — 4 phases with wall-clock metrics.
norunSoloPairedMode (pairedMode.ts)Federated: this process drives only its own leg; the peer middleware drives the other. See Federation.
middleware → both legs + broker

Step 8 — The conversation (centralized flavor)

runDemoFlow phases, each wrapped in timePhase() which publishes phase.started/phase.ended:

  1. voice_intro — up to 4 alternating turns. Per turn, llm.respondVoiceTurn() returns {speak, wantsToSwitch}; the line is spoken on the speaker's leg via speak(). Loop exits early once BOTH sides have said wantsToSwitch=true.
  2. data_exchange — the orchestrator opens two client WSes to /data/<sessionId> (one per agent), seeds history with the voice transcript as a pseudo-reply, sends both hellos, then alternates llm.respondJson() turns (max 6, 30s deadline) until a bye. It force-sends bye on both WSes if the loop ended without one, so the relay closes cleanly.
  3. voice_goodbye — per leg, llm.respondText() over the full transcript → one spoken farewell sentence (hardcoded fallback only if the LLM call throws).
  4. hangup — plivoClient.hangup() per leg via REST; <Wait>/keepCallAlive would otherwise hold the legs open. Finally publishSummary() computes the cost/latency panel (voice baseline = dataTurns × observed voice sec/turn) and signalDemoComplete releases any parked legs.
variant

Step 9 — The human variant

A human dials DID A or B directly. Steps 3–4 run unchanged (callee XML, WS opens, responder role). The handshake hears no preamble for 8s — and because responders never emit first, the human hears no beeps. On timeout: call.mode=human_to_agent, handshake.timeout, then runVoiceMode:

greet (persona-fixed line, e.g. "Hi, this is Anil from Mumbai Fresh Produce…")
loop: media frames → stt.feed() buffers until ~1.4s speech + 500ms silence
      → whisper transcript → llm.respondText(persona, history) → tts → speak
until WS closes or the provider sends event:"stop" → REST hangup

The pre-Dial-topology build had a bug here worth remembering: every inbound call computed a deterministic conference name, so the state machine waited 15s for a conference peer, failed, and hung up on the human. The current fallback is timeout → greet.

Event stream a successful A↔A call produces

call.triggered → handshake.started (×2 legs) → call.mode(agent_to_agent) (×2)
→ handshake.peer_detected (×2) → handshake.paired → pairing.summary (×2)
→ phase.started(voice_intro) → voice.transcript… → phase.ended
→ phase.started(data_exchange) → agent.message… → phase.ended
→ phase.started(voice_goodbye) → voice.transcript… → phase.ended
→ demo.summary → call.ended (×2)

All of it flows through eventBus.publishDemo → the SSE route /api/events → Dashboard.tsx (and, in federation, is also POSTed to the leader's /api/forward-event).
